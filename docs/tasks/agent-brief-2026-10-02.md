## 2. Проблемы (с доказательствами, а не «кажется»)

### П-1. КРИТИЧНО: активность ребёнка пропадает и сама возвращается
Слова владельца: «данные об активности ребенка снова пропали», затем «сейчас активность снова
открылась. но в любом случае это надо проверять».

Причина установлена чтением кода:
- Детское приложение каждые ~2 минуты снимает новый снимок активности и отправляет его как
  **самый свежий** статус устройства; сервер отдаёт родителю **только самый свежий** статус.
  Значит любой неудачный снимок **затирает** предыдущий удачный — до следующего удачного,
  поэтому данные «пропадают и сами возвращаются».
- Три источника пустого снимка:
  1. `parentwatch/src/main/java/ru/example/parentwatch/utils/DeviceInfoCollector.kt:140-151` —
     в ветке «разрешение не выдано» в JSON **нет ключа `dailyUsage`**, и этот результат
     **пишется в кэш** (`cachedAppUsageJson`). Дальше `:61` кладёт
     `appUsage.optJSONObject("dailyUsage") ?: JSONObject()` — пустой объект, который родитель
     принимает за «данных нет».
  2. `parentwatch/src/main/java/ru/example/parentwatch/service/AppUsageTracker.kt:257` —
     `available = sawEvent`: пустой журнал событий Android (долгая блокировка, поворот журнала)
     даёт снимок «данных нет» без списка приложений.
  3. `AppUsageTracker.kt:252-256` — приложения фильтруются по «есть запуск с рабочего стола»;
     если за день остались только отфильтрованные, список пуст при `available = true`.
- На стороне родителя это добивается тем, что `app/src/main/java/ru/example/childwatch/DeviceUsageActivity.kt:113-116`
  **предпочитает самый свежий снимок, даже если он пустой** (пустой `{}` — тоже `Map`,
  поэтому проверка его пропускает вперёд хороших данных из истории).

Что требуется: пустой или неполный снимок **никогда не заменяет** последний удачный —
ни в кэше детского приложения, ни в том, что видит родитель; хранить время удачного снимка
и честно показывать «данные за HH:mm». Проверено на телефоне Лёвы: разрешение на месте
(`GET_USAGE_STATS: allow`), приложение работает — то есть дело не в разрешении.

### П-2. Экран активности: мало данных, нет точного времени
Слова владельца: «надо проверять а также улучшать отображение, больше данных нужно, сейчас
не указывается точного времени и так далее».

Сейчас в строках приложений за день (`DeviceUsageActivity.kt:184-197`) показываются только
длительность и проценты, `subtitle` пустой; в «недавних» (`:228-244`) время относительное
(«5 мин назад»). При этом детское приложение **уже присылает** `lastUsed` (точная метка времени)
и `totalTimeInForeground` по каждому приложению — данные есть, их просто не показывают.
Нужно: точное время (`14:20`) по каждому приложению, заметная сумма за день, число приложений,
время первого и последнего использования за день.

## 3. Задачи (реализовать)

### З-1. История активности по дням — серверная часть (главное)
Сейчас видно только «сегодня». Сделать накопление **по дням за три месяца** (срок уже выбран
владельцем):
- при каждом статусе устройства **вкладывать** снимок дня в накопленную таблицу, а не
  перезаписывать день: по каждому пакету хранить максимум `totalTimeInForeground` и максимум
  `lastUsed`, имя обновлять только непустым, **никогда не писать нули и не уменьшать накопленное**;
- пустой/неполный снимок (`нет apps`, `available == false`, нет `start`/`end`, суммарное время
  ноль, `appUsageStale == true`) — **полностью игнорировать**, но сам статус устройства
  принимать как раньше;
- день считать по часовому поясу `dailyUsage.timeZone`, который присылает детское приложение,
  хранить как `YYYY-MM-DD`; учесть переход через полночь;
- привязка к семье и участнику, чужие данные не видны;
- миграция штатная, в стиле `server/database/DatabaseManager.js` (образец —
  `chat_group_conversation_type_v1`); ничего не удалять;
- удаление старше 90 дней — отдельной явной задачей (при старте и раз в сутки) с записью в лог,
  срок настраивается переменной окружения;
- API для родителя: активность за конкретный день и суммы по дням за период (для графика),
  в стиле существующих маршрутов и с той же авторизацией;
- проверка — скриптом в стиле `server/scripts/verify-group-conversations.js`, обязательно с
  ловушками: хороший снимок + пустой → день цел; `appUsageStale` → игнор; тот же снимок трижды →
  время не удвоилось; рост в течение дня → максимум; полночь и разные пояса; чужая семья не видна;
  очистка старше 90 дней. Вывод скрипта приложить дословно.

### З-2. Аналитика перемещений — сначала план, потом код
Замысел владельца: «фитнес-аналитика, но про перемещения» — сколько и где человек двигался.
Нужно: расстояние за день отдельно пешком и на транспорте, время в движении и на месте, карта
частых мест и обычных маршрутов, история по дням за три месяца, «пришёл/ушёл» из важных мест.
Сначала изучить, что уже есть (`server/services/LocationMotionStore.js`,
`server/services/FamilyPlacesService.js`, `design-system/.../MapRouteSegments.java`, `MapSpeed.java`,
очередь отправки точек в детском приложении), затем дать план: таблицы, алгоритмы (фильтр мусора GPS,
пороги скорости, остановки, защита от двойного счёта и от повторной отправки), API, что показывают
оба приложения, расход батареи и объёма, порядок работ с рисками. Файлы карты не менять — там
работает другой агент.

### З-3. Кнопка выпуска: защита от понижения версии
`scripts/release-updates.ps1` сейчас **не проверяет**, что выпускаемая версия новее уже
опубликованной. Номер версии = число коммитов, поэтому кнопка может случайно выложить **старую**
сборку вместо новой. Добавить проверку и остановку с понятным сообщением.

### З-4. Скрипт выкладки сервера: починить вывод лога запуска
`scripts/deploy-server.ps1` в блоке перезапуска печатает
`MARK : The term 'MARK' is not recognized` — лог запуска сервера из-за этого не виден, и нельзя
убедиться, что сервер поднялся. Починить так, чтобы лог действительно показывался.
