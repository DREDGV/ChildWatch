# Обновление приложений по воздуху

## Зачем

Сейчас каждая сборка ставится руками: подключить телефон проводом, собрать, скопировать,
установить. На боевом детском телефоне это отдельная поездка, а на телефоне ребёнка —
вообще невозможно без доступа к нему. Из-за этого исправления подолгу не доходят до
устройств, а версии на телефонах расходятся.

## Что берём из проекта ruvia

Механизм там рабочий, и главное в нём сделано правильно. Берём:

1. **Один манифест версии** как единственный источник правды о том, что опубликовано.
2. **Сравнение целым числом**, а не строкой: у нас код версии и так целое (метка времени),
   это надёжнее любых разборов строк.
3. **Проверку SHA-256** скачанного файла **до** установки, причём из того же манифеста.
4. **Проверку подписи**: скачанный файл должен быть подписан **тем же ключом**, что и
   установленное приложение, и совпадать по имени пакета. Это защита от подмены.
5. **Тихий поиск обновления**: неудача сети не должна мешать работе приложения.
6. **Установку через системный установщик** с показом подтверждения человеку.

## Что делаем иначе — потому что в ruvia это слабое место

| Слабое место в ruvia | Как делаем у нас |
|---|---|
| Регулярное выражение версии **жёстко привязано к `-alpha`**: уйдя с альфы, обновления молча перестают приходить | Версию сравниваем **по числу**, строку не разбираем вообще |
| Неудачная проверка **запоминается как успешная** — час тишины после сетевой ошибки | Метку времени двигаем **только при успехе**; ошибка даёт повтор при следующем запуске |
| Установка не **отменяет** неудавшуюся сессию установщика | Сессию закрываем в любом исходе, иначе следующая попытка упрётся в занятую сессию |
| Решение «повторить или нет» принимается по **поиску слова «checksum» в тексте ошибки** | Различаем причины **кодом**, а не текстом |
| Для скачивания **браузером** контрольная сумма не проверяется | Страница отдаёт сумму, и она же есть в манифесте — расхождение видно |
| Нет **ограничения частоты** на раздаче файлов | Ограничиваем частоту обращения к манифесту и к файлу |
| Раздача опирается на **точные пути nginx** и вручную заданные заголовки | У нас Express, поэтому задаём типы и заголовки явно |

## Устройство

### Манифест

`GET /api/updates/manifest` — без авторизации (телефон может проверять обновление до входа).

```json
{
  "schema": 1,
  "generatedAt": 1789000000000,
  "apps": {
    "parent": {
      "packageName": "ru.example.childwatch",
      "versionCode": 1789000000,
      "versionName": "7.3.26264.005538",
      "sizeBytes": 44564480,
      "sha256": "…",
      "file": "/updates/ParentMonitor-7.3.26264.005538.apk",
      "signingCertSha256": "…",
      "notes": "Что изменилось, коротко"
    },
    "child": { "…": "…" }
  }
}
```

### Файлы

`GET /updates/files/<имя>.apk` — раздаётся **нашим Express**, а не через Apache на том
же сервере. Причина простая: Express уже держит HTTPS для нашего API, поэтому меньше
движущихся частей и один сертификат. Второй веб-сервер пришлось бы держать синхронным
с первым, и однажды они разойдутся.

Заголовок `Content-Type: application/vnd.android.package-archive`, `Content-Disposition:
attachment`, поддержка частичного скачивания (иначе большой файл не докачается при обрыве
связи). Имя файла проверяется по строгому образцу, поэтому выход из каталога невозможен.

**Каталог выпусков лежит вне приложения** и задаётся переменной `CW_UPDATE_DIR`:

| Где | Что | Почему |
|---|---|---|
| на сервере | `/var/www/childwatch-updates` | выкладка новой версии сервера **не должна стирать** выпущенные сборки |
| при разработке | `updates/` в корне проекта | чтобы можно было проверить всё локально |

Это не прихоть: если положить выпуски внутрь приложения, первая же выкладка сервера
их удалит — а телефоны в этот момент будут их скачивать.

**Манифест отдаётся с `no-store`.** Кэшированный манифест — это не мелочь
производительности, а ошибка: он скроет только что выпущенную версию или продолжит
объявлять уже установленную. Файл выпуска, наоборот, кэшируется надолго: его имя
меняется с каждой сборкой, а содержимое неизменно.

### В манифесте есть готовый адрес файла

Сервер подставляет поле `url` рядом с именем файла. Это сделано, чтобы клиент **не
собирал адрес сам**: в ruvia он собирает, и имя файла из манифеста не читается вообще —
переименование пришлось бы делать в трёх местах, и ничто не поймало бы расхождение.


### Что делает приложение

1. При запуске, **не блокируя** интерфейс и не чаще раза в сутки — запрос манифеста.
2. Сравнение: `манифест.versionCode > текущий.versionCode` — и только тогда есть обновление.
3. Показ **уведомления** в приложении, без навязывания: человек сам решает, когда ставить.
4. По согласию — скачивание с проверкой:
   - размер совпал;
   - **SHA-256 совпал** — иначе файл удаляется и установка не предлагается;
   - **подпись и имя пакета совпали** с установленным приложением;
   - только после этого — системный установщик.
5. Результат установки обрабатывается **отдельным приёмником**, объявленным в манифесте:
   при замене приложения процесс убивается, и обычный код результата не увидит.

### Чего сознательно НЕ делаем

- **Не ставим обновление молча.** Android всё равно требует подтверждения для обычного
  приложения, а тихая установка требует особых прав. Показываем человеку и объясняем.
- **Не тянем обновление по мобильной сети** без согласия: 45 МБ — это заметно. Спрашиваем
  или ждём Wi-Fi.
- **Не публикуем ключ подписи** и не храним его пароль в репозитории.

## Порядок внедрения

1. Серверная часть: манифест, раздача файлов, ограничение частоты.
2. Сборка: при сборке выпускаемой версии считать SHA-256 и подпись, складывать в манифест.
3. Клиент: тихая проверка и уведомление.
4. Клиент: скачивание с проверками и установка.
5. Документ для человека: как выпустить обновление одной командой.

## Что нужно от владельца

1. **Постоянный ключ подписи.** Сейчас сборки отладочные; для обновлений «поверх» нужен
   один и тот же ключ навсегда, иначе Android откажется ставить обновление поверх
   приложения, подписанного другим ключом. Пароль от ключа в репозиторий не кладу.
2. Решение: **раздавать файлы через наш Express** (проще, всё в одном месте) или через
   Apache на том же сервере.

## Как обращаться с ключом подписи

Порядок взят из проекта ruvia, где он **проверен на практике**, и он решает ровно нашу
задачу: **я работаю, но секрета не вижу**.

### Ключ создаётся один раз и навсегда

Сменить его потом **нельзя без потерь**: Android поставит обновление только поверх сборки,
подписанной **тем же** ключом. Иначе человеку придётся **удалить приложение** — а вместе с
ним уйдут все данные. Сейчас у нас отладочные сборки, то есть **момент идеальный**: пока
приложение не разошлось по телефон��м, ключ можно завести без последствий.

### Где что лежит

| Что | Где | Почему |
|---|---|---|
| Ключ | вне проекта, в **личной папке владельца** | не исходный код, в репозиторий не попадает |
| Пароль | **зашифрованный средствами Windows** файл, привязанный к учётной записи владельца | я его **не читаю вообще** — просто запускаю сборку |
| Защита | `*.jks`, `*.keystore`, `*.p12`, `keystore.properties`, `*.dpapi` в правилах игнорирования | чтобы не улетел на GitHub случайно |

**Как это работает:** отдельный помощник создаёт ключ и сохраняет пароль в зашифрованный
файл. Дальше сборка сама его оттуда берёт. **Я запускаю скрипт и пароля не вижу** — секрет
остаётся в хранилище системы, а мне достаётся только инструмент. Это и есть ответ на
вопрос «как дать агенту работать, не отдавая секрет».

### Сборка обязана сверять отпечаток

Скрипт сборки **принимает ожидаемый отпечаток сертификата и отказывается публиковать**
файл, подписанный другим ключом. Без этой проверки однажды соберут «чем попало», и
обновление не встанет ни на один телефон. Проверка уже заложена в `scripts/stage-release.ps1`:
отпечаток попадает в манифест, и клиент сможет с ним свериться.

### Запасная копия — обязательна

**Ключ и пароль нужно сохранить на отдельный носитель.** Потеря ключа означает, что
**всем телефонам придётся переустанавливать приложение**. Это единственный необратимый
шаг во всей затее, поэтому копия — не формальность.

### Чего у меня быть не должно

Ни пароля от ключа, ни личных ключей владельца, ни доступа к панели хостинга и аварийной
консоли. **Развёртывание — только скриптом**, с копией конфигов и базы, проверкой
конфигурации до перезапуска и откатом при ошибке. Никаких «поправлю файл на сервере руками».


## Разбор ruvia: что там сделано сильно

Механизм там рабочий, и это стоит признать прямо:

- **TLS с закреплённым сертификатом**, а не системным хранилищем — для манифеста и для
  файла одинаково. Подменить ответ по дороге нельзя, не имея закрытого ключа узла.
- **Сумма публикуется в том же доверенном ответе**, что и версия, поэтому её нельзя
  подсунуть из другого источника.
- **Проверка подписи скачанного файла** против установленного приложения, плюс имя пакета
  и точное совпадение кода версии. Это строже, чем «Android и так не даст откатиться»:
  человек получает понятное сообщение вместо системной ошибки.
- **Сборка отказывается публиковаться**, если подпись не совпала с ожидаемым отпечатком;
  пароль от ключа передаётся только через окружение дочернего процесса.
- **Файл с теми же именем, но другим содержимым не перезаписывается** — иначе телефоны,
  уже начавшие скачивание, получили бы не то, что обещает манифест.
- **Результат установки ловит приёмник, объявленный в манифесте**: при замене приложения
  процесс убивается, и обычный код результата ничего не увидит.

## Разбор ruvia: чего избегаем — это их слабые места

Список составлен по коду, а не по документации (она там отстала от кода и описывает
поведение до 0.1.39, когда приложение ещё не скачивало обновления само).

| Слабость | Последствие | У нас |
|---|---|---|
| Форма версии **жёстко `-alpha`** и в клиенте, и в проверке манифеста | уйдя с альфы, **все установленные приложения молча перестают видеть обновления** — уведомление просто исчезает | версию **не разбираем строкой вообще**, сравниваем целое число |
| Метка проверки ставится **до** запроса | одна сетевая ошибка — **час тишины**, повтора нет | метку двигаем **только при успехе** |
| Сессия установщика **не закрывается** при ошибке | Android ограничивает число живых сессий — следующая попытка упрётся в занятую | закрываем в любом исходе |
| «Повторить или нет» — по **поиску слова в тексте** ошибки | переформулировали сообщение — **изменился совет человеку** | различаем **типом** ошибки |
| Проверка суммы **только для приложения**, для страницы-скачивания — нет | человек, скачавший браузером и пропустивший сверку, получает что даст цепочка сертификатов | сумму показываем и в манифесте, и на странице |
| Нет **ограничения частоты** на раздаче файлов | один клиент может тянуть файл без конца | ограничение есть |
| Окно загрузки **нельзя отменить**, прогресс только при известной длине | при потоковом ответе — вечное «идёт загрузка» без выхода | отмена и прогресс без опоры на длину |
| Закреплённый сертификат проверяется на **срок действия** | истёк сертификат — **все проверки молча ничего не находят** | следим за сроком отдельно |
| Тесты проверяют **текст исходников**, а не поведение | переименовали переменную — тест «сломался», а поведение не проверено | проверяем поведение |
| Документ описывает **старое** поведение и ссылается на **несуществующий** файл | следующий разработчик восстановит устаревшую схему | документ рядом с кодом, проверяем при изменении |

Отдельно: у них раздача опирается на **точные пути nginx** и вручную заданные заголовки.
У нас Express, поэтому типы и заголовки задаются явно в маршруте, а не полагаются на
поведение по умолчанию: раздача каталога целиком показала бы всё, что в нём лежит.

## Мелочи, которые стоит повторить из ruvia

- **Закрывать отдачу каталога**: отдавать конкретные файлы, а не папку целиком, иначе
  становятся видны и резервные копии.
- **Манифест — `no-store`.** Кэшированный манифест скрывает свежий выпуск или продолжает
  объявлять уже установленный. Файл выпуска, наоборот, кэшировать можно: его имя меняется
  с каждой сборкой, а содержимое не меняется никогда.
- **Проверять конфигурацию сервера до перезапуска**, а не после.
- **Выкладывать через свежий каталог**, а не поверх старого: иначе в раздаче остаются
  файлы прошлых выпусков.
