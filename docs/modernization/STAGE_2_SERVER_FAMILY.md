## Миграция и совместимость

Миграция встроена в существующий `DatabaseManager.createTables()` и выполняется автоматически после создания/обновления текущих таблиц.

1. Четыре новые таблицы и их индексы создаются через `CREATE TABLE/INDEX IF NOT EXISTS`.
2. Активные строки `device_links` объединяются в компоненты связанных устройств.
3. Для каждой компоненты создаётся или повторно используется одна активная семья.
4. Идентификаторы семьи, участника, семейного устройства и разрешения вычисляются детерминированно через SHA-256.
5. Bootstrap выполняется в транзакции и сериализован очередью, поэтому параллельные регистрации не начинают конкурирующие миграции.
6. Повторный bootstrap использует UPSERT и не создаёт дублей.
7. Явно запрещённое разрешение не включается заново при следующем старте сервера.
8. Если новый legacy-link соединяет две прежние семьи, одна семья становится основной, а прежние записи второй сохраняются неактивными. Данные не удаляются.
9. Частые повторные WebSocket-регистрации не запускают полный bootstrap: он повторяется только для новой или вновь активированной связи.
10. `device_links` остаётся рабочим compatibility-источником и не удаляется.

Ограничение bootstrap: старая pair-based модель не отличает человека от его телефона. Поэтому при первичном переносе для каждого legacy-устройства создаётся отдельный участник и отдельная запись устройства. Новая схема уже разделяет эти сущности и позволяет уточнить их позднее.

## API contract

Все адреса требуют действующий `Authorization: Bearer <token>`. Устройство может читать только семью, в которой присутствует его активная запись `family_devices`.

| Метод | Адрес | Успешный ответ |
|---|---|---|
| `GET` | `/api/families` | `{ success, families[] }` |
| `GET` | `/api/families/:familyId` | `{ success, family }` |
| `GET` | `/api/families/:familyId/members` | `{ success, familyId, members[] }` |
| `GET` | `/api/families/:familyId/devices` | `{ success, familyId, devices[] }` |

Основные ошибки:

- `400 INVALID_FAMILY_ID` — недопустимый формат идентификатора;
- `401` от общего `AuthMiddleware` — отсутствующий или недействительный токен;
- `403 FAMILY_ACCESS_DENIED` — устройство не входит в указанную семью;
- `404 FAMILY_NOT_FOUND` — активная семья не найдена.

Ответы не содержат токены, хеши сессий, аудио, фотографии или координаты.

## Permission service

`FamilyPermissionService` принимает реальный `actorDeviceId`, реальный `targetDeviceId` и имя функции. Решение по умолчанию закрытое:

- неизвестная функция запрещена;
- устройства из разных семей получают `CROSS_FAMILY_DENIED`;
- отсутствие явного разрешения означает запрет;
- разрешение читается по паре `actor_member_id -> target_member_id` внутри общей активной семьи.

Для совместимости bootstrap создаёт разрешения, соответствующие существующей связи родитель—ребёнок. Сервис подготовлен для следующих этапов, но существующие audio/photo/chat маршруты ещё не переключены на него.

## Точная WebSocket-адресация

В `WebSocketManager` добавлен `deviceSockets: Map<deviceId, Set<socketId>>` и операции:

- `registerDeviceSocket`;
- `unregisterDeviceSocket`;
- `getConnectedSocketIdsForDevice`;
- `emitToExactDevice`.

Оба типа приложения регистрируют реальный authenticated `deviceId`. Несколько живых сокетов одного телефона допускаются во время перекрывающегося reconnect. Отключение старого сокета удаляет только его и не повреждает новое соединение. `emitToExactDevice` возвращает число доставок и никогда не перенаправляет событие на единственное другое подключённое устройство.

Проверенная legacy-аудиомаршрутизация через `childSockets`/`parentSockets` оставлена без изменения.
