# Запись в текст: собственный сервер и проверка

Готовая голосовая запись в существующем composer открывает действия «Прослушать» и «Запись в текст». Последнее доступно при поддержке действующего сервера; сохранённый результат можно открыть и после выключения worker. Распознавание начинается отдельным нажатием. Полученный текст редактируется и отправляется только кнопкой пользователя. При ошибке распознавания исходная запись остаётся доступна для отправки голосом.

## Приватные задания и обработка

POST `/api/chat/v2/conversations/:id/transcriptions`: multipart `file`, `clientRequestId`, `language=ru`, `durationMs`. GET и DELETE `/api/chat/v2/conversations/:id/transcriptions/by-client/:clientRequestId` читают результат и отменяют задание. Все маршруты используют существующую авторизацию беседы; доступен только собственный запрос текущего участника с точным устройством и семьёй. Возврат результата снова проверяет действующее членство.

SQLite сохраняет задания QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED, входную контрольную сумму и стабильный ID. Повтор того же содержимого возвращает прежнее задание; изменённое содержимое с тем же ID отклоняется. Очередь ограничена 20 ожидающими/работающими заданиями всего и тремя на устройство. Один worker использует lease и проверяет права до обработки, во время неё и внутри транзакции публикации. После рестарта очередь восстанавливается; прежний worker не может опубликовать результат после потери lease.

Для Linux каждый процесс FFmpeg/whisper запускается через `scripts/transcription-exec-guard.py`: Python устанавливает kernel parent-death SIGKILL, проверяет PID родителя до и после установки и затем выполняет exec без shell. Привилегированные исполняемые файлы отклоняются. Проверяется настоящая доступность guard и его контрольная сумма. Истёкший lease живого controller не передаётся второму worker: PID проверяется вместе с временем старта из `/proc`, без уничтожения сторонних процессов. Windows допускает прямую локальную проверку модели, но production capability на Windows не включается.

Worker декодирует M4A через FFmpeg, проверяет фактическую длительность PCM, затем вызывает CPU whisper.cpp с многоязычной моделью `base`, русским языком и двумя потоками. Предел обработки — десять минут на всю цепочку, входа — 10 МиБ, длительности — 180 секунд, текста — 16 КиБ. Команды запускаются без shell; M4A не может подключать внешние файлы или сетевые протоколы. Промежуточные PCM/WAV/JSON удаляются сразу, приватная копия входного аудио — через час после завершения/отмены. Вложение уже отправленного голосового сообщения хранится отдельно и этой очисткой не удаляется. Внешний сервис распознавания не используется.

## Клиенты и обновление базы

Room обеих программ повышен 13→14, добавлена и зарегистрирована самостоятельная миграция. Старые миграции не менялись. `chat_transcriptions_v2` хранит точный server/family/member/device scope, исходное аудио, состояние задания и редактируемый текст. Поллинг обновляет поля результата, сохраняя правки пользователя; подтверждённый отказ в доступе очищает распознанный и исправленный текст, поздняя правка не восстанавливает его.

Уход экрана в фон закрывает окно и сохраняет последнее исправление. Возврат читает состояние по прежнему ID, автоматически не загружает новую запись и не отправляет сообщение. Отмена может прервать текущую загрузку; потеря ответа не объявляется подтверждённой отменой. Текст получает стабильный `draftId:text` в существующем outbox; повтор после прерывания использует уже сохранённое сообщение. Только после durable постановки текста в очередь расходуется локальный голосовой черновик. «Добавлен в очередь» не означает доставку собеседнику.

- Сервер транскрибации: 15/15 PASS; ещё три Linux-only проверки честно пропущены на Windows, `.runtime/chat-transcriptions-server-2026-10-10-guard-final.log`. Проверены приватность/отзыв, идемпотентность, SQLite close/reopen, отмена, TTL, очередь, bounds реальных subprocess и неполный benchmark proof. Регрессия прежних attachments/HTTP/socket/edit-delete: 44/44 PASS, `.runtime/chat-transcription-chat-regression-2026-10-10.log`. Kernel parent-death и удержание lease на Linux пока требуют запуска там; WSL на этом ПК отсутствует и не устанавливался.
- SQL fixtures обеих shipped баз 12→14 и 13→14: сохранение истории/черновиков/исправлений/метки отправки, точный scope, очистка после отказа и foreign keys/integrity — PASS, `.runtime/chat-transcription-migration-sql.txt`. Это не настоящий Room upgrade на телефоне.
- Реальная цепочка FFmpeg→whisper.cpp `base` проверена на синтезированной локально русской фразе без детского аудио. 12,505 секунды записи → 5,846 секунды обработки; 17 слов, 0 замен/вставок/удалений после нормализации регистра, пунктуации и ё/е. Это чистый синтетический пример, не оценка полевой точности.
- Повтор той же нейтральной фразы на 175 секунд → 26,099 секунды обработки. Измеренный Windows PeakWorkingSet: engine 431566848 байт, Node 33718272 байт, консервативная сумма 465285120 байт (≈444 МиБ). Опрос только PID этой цепочки каждые 50 мс. Реальный сервер имеет другие процессы и нагрузку; эти числа не разрешают включать функцию на VPS.
- 181 секунда реального M4A → `422 TRANSCRIPTION_INVALID_DURATION` до запуска whisper. В каждом успешном и отклонённом сценарии каталог промежуточных файлов пуст. Файлы свидетельств: `.runtime/transcription-engine/*-result.json`, `*-memory.json`, `neutral-too-long-probe.log`, `verification.json`.
- Официальный Windows whisper build b5454 и многоязычная `ggml-base.bin` скачаны в игнорируемую `.runtime`, хеши сверены с опубликованными метаданными. Происхождение записано в `.runtime/transcription-engine/sources.json`. Системные программы не устанавливались, голосовая фраза никуда не отправлялась.

## Серверный порядок перед включением

Сначала подготовить консистентный бэкап существующей базы и приватных папок. Общая серверная основа этапа вложений: `database/DatabaseManager.js`, `services/ChatAttachmentStore.js`, `services/ChatConversationService.js`, `routes/chat-v2.js`, `routes/chat-attachments.js`. Поверх неё нужны новые `services/ChatTranscriptionService.js`, `services/ChatTranscriptionRunner.js`, `routes/chat-transcriptions.js`, `scripts/transcription-exec-guard.py` и `scripts/benchmark-chat-transcription.js`. Клиенту без capability кнопка распознавания не показывается.

Папка `CHAT_TRANSCRIPTION_ROOT` (по умолчанию `server/private-data/chat-transcriptions`) должна находиться вне static/nginx root. Переменные `CHAT_TRANSCRIPTION_FFMPEG`, `CHAT_TRANSCRIPTION_WHISPER`, `CHAT_TRANSCRIPTION_MODEL`, `CHAT_TRANSCRIPTION_BENCHMARK` — абсолютные пути. `CHAT_TRANSCRIPTION_MEMORY_BUDGET_BYTES` задаётся по действительно свободной памяти с запасом для работающего ChildWatch. По умолчанию `CHAT_TRANSCRIPTION_ENABLED` не включён.

Нужен системный Python 3: `CHAT_TRANSCRIPTION_PYTHON` по умолчанию `/usr/bin/python3`, `CHAT_TRANSCRIPTION_GUARD` по умолчанию указывает на shipped `scripts/transcription-exec-guard.py`. Сначала на Linux запустить `node node_modules/jest/bin/jest.js --runInBand __tests__/chat-transcriptions.test.js`: все 18 проверок, включая принудительное завершение изолированного fixture-controller и отсутствие его дочернего процесса, должны пройти. Проверка не завершает рабочий ChildWatch. Benchmark включает probe kernel guard и хеши Python/helper в свой proof; отсутствие guard запрещает включение независимо от остальных метрик.

На самом Linux VPS запустить `node scripts/benchmark-chat-transcription.js /absolute/path/neutral-175s.m4a`. Скрипт не включает функцию и не меняет работающий сервер. Он измеряет реальную обработку, память, контрольные суммы/хост, а также `/api/health` до и во время работы. Проверка требует минимум пять фоновых и три нагрузочных пробы; P95 не выше заданного бюджета (по умолчанию 1000 мс) и не выше `max(100 мс; 3 × baseline P95)`. Неполный или чужой proof не разрешает capability. Только после успешного измерения и проверки запаса ресурсов владелец отдельно устанавливает `CHAT_TRANSCRIPTION_ENABLED=1` и перезапускает ChildWatch.

В этой сессии SSH с включённым VPN завершился таймаутом (`.runtime/transcription-vps-access-2026-10-10.txt`). Сервер, APK, подписи, телефоны и VPN не менялись. Ресурсный benchmark на VPS, настоящий Room upgrade, внешний вид диалога, запись/распознавание/исправление/отправка между телефоном ребёнка и родителя остаются непроверенными; текущий статус и конкретное продолжение находятся в TODO.md.
